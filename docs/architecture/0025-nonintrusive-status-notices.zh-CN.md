# 兼容状态提醒的分级与去重

2026-11-02。修复初始化等待和源码更新被当作故障、同一问题反复弹窗的体验。只更新状态监测和自有 Mac 入口；ChatGPT、页面 helper 与网关没有被重启。

## 原因

用户的新截图确实来自重启后的主客户端：PID 37552、helper 37609 于 13:34 启动，新健康报告存在且持续报告 pending。因此这次不能继续解释为旧 helper 未加载监测代码。原展示逻辑把初始化等待超过 45 秒、报告未知等情况全部映射成 warning。

原通知器用详细错误串作为事件身份，重检会重新创建它，短暂恢复又立即清空去重；原生入口在再次点击图标时也会主动打开警告窗。这些路径会把同一个未恢复问题重新提醒。另一个会话修改共享网关源码后，版本差异还被误显示为后端故障。

## 新行为

- 等待初始化、未上报、报告过期、报告无法读取和连接重试属于待确认状态：显示 info 和菜单栏文字，不声称已经正常，也不自动弹窗。
- 源码比运行版本新属于更新待加载。只读监测会对已有私有网关进行认证连接检查；连通时显示“运行中”，代码更新不触发故障提醒。连接确实失败时仍进入故障路径，不用更新待加载掩盖断连。
- 确认的故障按 backend / page / monitor 等功能身份提醒一次，详细错误原因变化仍视为同一未恢复问题。
- 原生入口使用按配置文件隔离的 UserDefaults 保存已经提示的功能。关闭窗口后，重检、重开图标、菜单栏入口重启都不重新弹同一问题。手动“查看兼容状态…”始终可以打开详情。
- 功能稳定恢复 30 秒后才允许再次产生新故障事件。恢复只在菜单栏短暂显示，不再自动打开大窗口。后端恢复不会清除一个尚未恢复的页面问题。
- 再点 MyCodex 图标只执行原有打开/激活流程；现有监测仍存活时复用它，不因重开重置去重。源码更新待加载不走启动失败弹窗。

实际 UI 注意力由原生 `StatusAttention` 管理；Node 的 notice 是兼容事件提示，不绕过原生持久去重。原生策略与展示代码位于同一 Swift 文件，没有新增后台服务或框架依赖。
